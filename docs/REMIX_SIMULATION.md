# 1️⃣3️⃣ Virtual Simulation Using Remix IDE

## Step-by-Step Remix Simulation Guide

This guide walks you through testing the entire smart contract using **Remix IDE** (https://remix.ethereum.org) with the built-in Remix VM. No real ETH required.

---

## Account Setup

When you open Remix, the built-in VM provides several test accounts. Assign them as follows:

| Account | Role | Purpose |
|---------|------|---------|
| Account 1 (first in list) | **Patient** | Owns records, controls access |
| Account 2 (second in list) | **Doctor** | Requests access to records |
| Account 3 (third in list) | **Hospital** | Creates medical records |

> **TIP**: Copy each account address and label them in a text file for reference.

---

## Step 1: Open Remix IDE

1. Go to https://remix.ethereum.org
2. In the left panel, click **File Explorer**
3. Create a new file: `HealthcareDataExchange.sol`

📸 **Screenshot**: Remix IDE with new file created

---

## Step 2: Paste the Contract Code

1. Copy the entire content of `contracts/HealthcareDataExchange.sol` from this project
2. Paste it into the Remix editor

📸 **Screenshot**: Contract code in Remix editor

---

## Step 3: Compile the Contract

1. Click the **Solidity Compiler** tab (left panel, 2nd icon)
2. Select compiler version: **0.8.20**
3. Click **Compile HealthcareDataExchange.sol**
4. You should see a green checkmark ✅

📸 **Screenshot**: Successful compilation with green checkmark

---

## Step 4: Deploy the Contract

1. Click the **Deploy & Run Transactions** tab (left panel, 3rd icon)
2. Environment: Select **Remix VM (Cancun)** or **Remix VM (Shanghai)**
3. Account: Make sure any account is selected (the deployer becomes admin)
4. Click **Deploy**
5. The contract appears under **Deployed Contracts**

📸 **Screenshot**: Deployed contract visible in Remix

---

## Step 5: Register Patient (Account 1)

1. In the **Account** dropdown, select **Account 1** (Patient)
2. Expand the deployed contract
3. Find `registerPatient`
4. Enter: `"John Doe"`
5. Click **transact**
6. Check the transaction log — you should see the `UserRegistered` event

📸 **Screenshot**: Patient registration transaction + event log

---

## Step 6: Register Doctor (Account 2)

1. Switch to **Account 2** in the Account dropdown
2. Find `registerDoctor`
3. Enter: `"Dr. Sarah Smith"`
4. Click **transact**
5. Verify `UserRegistered` event in logs

📸 **Screenshot**: Doctor registration transaction + event log

---

## Step 7: Register Hospital (Account 3)

1. Switch to **Account 3** in the Account dropdown
2. Find `registerHospital`
3. Enter: `"City General Hospital"`
4. Click **transact**
5. Verify `UserRegistered` event in logs

📸 **Screenshot**: Hospital registration transaction + event log

---

## Step 8: Hospital Adds a Medical Record for the Patient

1. Stay on **Account 3** (Hospital)
2. Find `addMedicalRecord`
3. Enter the following parameters:
   - `_patient`: **Account 1's address** (copy from dropdown)
   - `_recordType`: `"Lab Report"`
   - `_fileHash`: `0x7f83b1657ff1fc53b92dc18148a1d65dfc2d4b1fa3d677284addd200126d9069`
   - `_storageRef`: `"ipfs://QmSimulated123"`
4. Click **transact**
5. Verify `MedicalRecordAdded` event

📸 **Screenshot**: Medical record added transaction + event log

> **Note**: The `_fileHash` is a dummy SHA-256 hash. In a real scenario, you'd use the hash generated by `generate-hash.js`.

---

## Step 9: Doctor Attempts Access BEFORE Permission

1. Switch to **Account 2** (Doctor)
2. Find `getRecord`
3. Enter: `1` (record ID)
4. Click **transact**
5. **Expected**: Transaction **REVERTS** with "Access denied: You do not have permission"

📸 **Screenshot**: Reverted transaction showing "Access denied" error

> This proves the access control is working — unauthorized doctors cannot view records.

---

## Step 10: Patient Grants Doctor Access

1. Switch to **Account 1** (Patient)
2. Find `grantAccess`
3. Enter:
   - `_doctor`: **Account 2's address** (Doctor)
   - `_recordId`: `1`
4. Click **transact**
5. Verify `AccessGranted` event

📸 **Screenshot**: Access granted transaction + event log

---

## Step 11: Doctor Accesses the Record (Now Authorized)

1. Switch to **Account 2** (Doctor)
2. Find `getRecord`
3. Enter: `1`
4. Click **transact**
5. **Expected**: Transaction **SUCCEEDS** — record metadata is returned
6. Verify `RecordAccessed` event

📸 **Screenshot**: Successful record access + returned data + event

---

## Step 12: Patient Revokes Doctor Access

1. Switch to **Account 1** (Patient)
2. Find `revokeAccess`
3. Enter:
   - `_doctor`: **Account 2's address**
   - `_recordId`: `1`
4. Click **transact**
5. Verify `AccessRevoked` event

📸 **Screenshot**: Access revoked transaction + event log

---

## Step 13: Doctor Attempts Access Again (Should Fail)

1. Switch to **Account 2** (Doctor)
2. Find `getRecord`
3. Enter: `1`
4. Click **transact**
5. **Expected**: Transaction **REVERTS** with "Access denied: You do not have permission"

📸 **Screenshot**: Reverted transaction showing access denied after revocation

> This proves revocation works — once a patient revokes access, the doctor can no longer view the record.

---

## Step 14: Check Event Logs

1. Click on any transaction in the Remix console
2. Expand the **logs** section
3. You should see all events that were emitted

### Expected Events in Order:
1. `UserRegistered` (Patient)
2. `UserRegistered` (Doctor)
3. `UserRegistered` (Hospital)
4. `MedicalRecordAdded` (Record 1)
5. `AccessGranted` (Patient → Doctor, Record 1)
6. `RecordAccessed` (Doctor accessed Record 1)
7. `AccessRevoked` (Patient revoked Doctor, Record 1)

📸 **Screenshot**: Event logs showing the complete audit trail

## Additional Verification Steps

3. Click **call**
4. **Expected**: Returns `true`
